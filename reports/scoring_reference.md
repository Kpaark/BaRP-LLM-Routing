# RouterBench Scoring Criteria Reference

Generated by `python -m barp.audit_scoring` (full stats in
`scoring_audit_family.csv` / `scoring_audit_eval_name.csv`).

RouterBench's `performance` column is **not** scored the same way across
components. Per-family quality numbers (our Table 2 / Table 3 replicas) mix
two different scales:

| Family        | Scoring     | Score values                 | Notes |
|---------------|-------------|------------------------------|-------|
| ARC-Challenge | binary      | {0, 1}                       | exact-match multiple choice |
| HellaSwag     | binary      | {0, 1}                       | exact-match multiple choice |
| MMLU          | binary      | {0, 1}                       | exact-match multiple choice |
| Winogrande    | binary      | {0, 1}                       | exact-match multiple choice |
| MBPP          | binary      | {0, 1}                       | code passes tests or not |
| GSM8K         | fractional  | {0, .25, .5, .75, 1}         | 99% of scores are partial credit |
| RAG           | fractional  | {0, .25, .5, .75, 1}         | ~16% partial credit |
| MT-Bench      | fractional  | {0.1 ... 1.0} (10 levels)    | rubric/judge score; never 0 |

## Implications for our results tables

1. **Cross-family averages mix scales.** The "Avg" column averages
   binary accuracies with rubric scores. That matches how the BaRP paper
   reports it, but a +1 point gain on GSM8K (partial credit) is not the
   same event as +1 point on MMLU (a full flip from wrong to right).

2. **MT-Bench's floor is 0.1, not 0.** Its judge rubric never awards 0,
   so MT-Bench numbers are slightly inflated relative to families where a
   wrong answer scores 0. (Only 80 prompts, so the effect on averages is
   small.)

3. **GSM8K is almost entirely partial credit** (99.25% of scores are
   strictly between 0 and 1). Its column reads as "average partial credit",
   not "% correct".

## Does this explain the HellaSwag discrepancy vs. the paper's Table 3?

**No.** HellaSwag is strictly binary exact-match in RouterBench --
same criterion as MBPP, where we matched the paper. So the
"different scoring scale" hypothesis is ruled out for HellaSwag: the gap
with the paper's number must come from elsewhere (checkpoint/steps,
encoder choice MiniLM vs MPNet, or which preference point the paper
reports). MBPP agreeing while HellaSwag differs is consistent with this:
both use the same binary scale, so scale can't be the differentiator.

## Practical convention going forward

* Report per-family columns as-is (matches the paper's convention).
* Annotate GSM8K / RAG / MT-Bench columns as fractional-credit in any
  writeup ("quality" = mean score, not accuracy).
* When claiming "X% of prompts answered correctly", restrict to the five
  binary families.
